# Releases

Releases use **Actions → Release → Run workflow** on `main`. The default is a
full rehearsal. Publishing is a separate, explicit selection on the same form.
Versions are stable `X.Y.Z` or beta `X.Y.Z-beta.N`. A beta is published as a
GitHub prerelease that never becomes the latest release. This flow does not
create npm releases.

Every release also runs [the complete dependency security checks](DEPENDENCY_SECURITY.md),
including development dependencies. The same checks run daily between releases.

## Store folders and what a merge publishes

The Home Assistant app store follows `main` of this repository and builds the
app on the user's machine. Every main commit that changes a store folder is an
app update for its users, with or without a GitHub release.

| Folder | App | Changes only in |
|---|---|---|
| `ha_app/` | **Eufy Security Viewer Bridge**, slug `eufy_viewer_bridge` | a stable release PR |
| `ha_app_beta/` | **Eufy Security Viewer Bridge (beta)**, slug `eufy_viewer_bridge_beta` | a beta cut or a stable release PR |

Both folders are generated by `scripts/prepare_ha_app.py` from `bridge/` and the
hand-edited app files in `app/`. Never edit them by hand. `ha_app_beta/` appears
with the first beta cut. Between those PRs the folders stay frozen, so merging a
runtime PR updates no app. Validate builds the candidate app from `bridge/` and
`app/` instead. `repository.yaml` is the store identity and never changes.

The store reads every tracked file whose name starts with `config.` and ends in
`.json`, `.yaml` or `.yml` as an app configuration. CI allows only `ha_app/config.json` and
`ha_app_beta/config.json`. The canonical configuration is therefore
`app/app_config.json`, without a version. The generator inserts the version.

HACS offers integration updates from published GitHub releases only. A merge
reaches HACS users after the Release workflow publishes it. A Release run does
not deploy to a Home Assistant instance.

## Versions and candidates

The integration version is the release version and names the tag. Release
`v0.8.46`, for example, contains integration 0.8.46 and bridge 0.8.37. A version
is published once the tag `v<version>` exists or a GitHub release uses that tag.
A bridge version counts as published once a store folder at the base carries it
or a newer version. Versions follow semver precedence: `0.8.47-beta.1` <
`0.8.47-beta.2` < `0.8.47` < `0.8.48-beta.1`. A beta takes its release notes from
the `X.Y.Z` section of its stable part. Documentation written in a PR names that
stable part.

`CHANGELOG.md` holds the integration sections and `app/CHANGELOG.md` the bridge
sections. Headings have two forms. `## X.Y.Z - Unreleased` marks an open batch.
`## X.Y.Z - YYYY-MM-DD` marks a batch dated by its release PR. CI rejects any
other heading that a PR adds. Older headings are never inspected or rewritten.

Bridge runtime changes are files under `bridge/src/`, `bridge/Dockerfile`,
`bridge/tsconfig.json`, every `bridge/package.json` key except `version`,
`description` and `devDependencies`, the production entries of
`bridge/package-lock.json`, and every file in `app/` except `README.md` and
`CHANGELOG.md`. Integration runtime changes are files under
`custom_components/eufy_viewer/`, including the card bundle, and every bridge
runtime change, because the bridge ZIP is a release asset. Validate applies
these rules to every PR against its base commit:

- The integration, bridge, client pin and store-folder versions never decrease.
- A PR with integration runtime changes leaves the integration at an
  unpublished version and changes the `CHANGELOG.md` section of its stable part.
  Several PRs accumulate in one candidate.
- A PR with bridge runtime changes also raises the bridge above every store
  folder version at the base, or keeps a bridge candidate that is already above
  them, and changes the `app/CHANGELOG.md` section of the bridge's stable part.
- A plain integration version reaches main only through a release PR, the PR
  that changes the version to `X.Y.Z`. It passes the release checks. A plain
  bridge version must equal the `ha_app/` version, so the bridge stays at a beta
  until the release PR.
- A dated section at the base closes that batch. A runtime PR must then raise
  the version, also while the release itself is not published yet.
- A changed client pin must match a verified client release. A beta client pin
  needs beta bridge and integration versions.
- On every commit, the versions satisfy `ha_app` ≤ `ha_app_beta` ≤ bridge, and
  the README card resource `?v=` is a plain version not above the integration.
- CI and documentation changes keep the versions. So do changes to
  `app/README.md` or `app/CHANGELOG.md` alone, which reach the store with the
  next regeneration of the store folders.

The usual sequence after the stable release `0.8.46` with bridge `0.8.37`:

| PR | Integration | Bridge | Changelogs |
|---|---|---|---|
| Integration runtime change | `0.8.47-beta.1` | keeps `0.8.37` | adds `## 0.8.47 - Unreleased` |
| Bridge runtime change | keeps `0.8.47-beta.1` while unpublished | `0.8.38-beta.1` | extends `0.8.47`, adds `## 0.8.38 - Unreleased` to `app/CHANGELOG.md` |
| Beta cut | keeps `0.8.47-beta.1` | keeps `0.8.38-beta.1`, writes `ha_app_beta/` at it | none |
| After `v0.8.47-beta.1` is public | `0.8.47-beta.2` | `0.8.38-beta.2` for a bridge change | extends the same sections |
| Release PR | `0.8.47` | `0.8.38`, both store folders at `0.8.38` | dates both sections |

When a runtime PR or a store-folder change keeps the base integration version,
CI looks up its tag and every page of GitHub releases with the workflow token.
A failed lookup fails the check. The release workflow creates the tag before its
draft, so the tag lookup also covers drafts that a read-only token cannot list.
A version above the base needs no lookup, because main never falls below a
published version. Rejections of a version below the base, the README card
version or a store version name the next valid version. So do rejections of a
closed batch, a plain integration version in a runtime PR, a plain bridge version
other than the `ha_app/` version, a published version and a bridge runtime
change without a newer bridge.

## Prepare a pull request

Make bridge and app changes in `bridge/` and `app/`, never in a store folder.
Set candidate versions in these places:

| Version | Files | How |
|---|---|---|
| Integration | `custom_components/eufy_viewer/manifest.json`, `pyproject.toml`, the project entry in `uv.lock` and the card bundle | edit the first two, run `uv lock`, then `npm run build` in `frontend/` |
| Bridge | `bridge/package.json` and the root of `bridge/package-lock.json` | `npm version X.Y.Z-beta.N --no-git-tag-version` in `bridge/` |
| Client pin | the client dependency in `bridge/package.json` and its lock entry | `python3 scripts/bump_client.py VERSION` |
| Card resource | the `?v=` examples in `README.md` | only in a release PR |

`uv lock` records a beta in its PEP 440 form, `0.8.47b1` for `0.8.47-beta.1`.
CI compares that form. Frontend builds must match the committed bundled
dashboard JavaScript. An integration-only candidate keeps the bridge version.

For a Mega library update, publish that library release first. Then run
`scripts/bump_client.py` with its version. It checks that the release is public,
is a prerelease exactly for a beta and has only the tarball, `SHA256SUMS` and
`release-manifest.json`, downloads them by asset ID and checks them against each
other and against the tag's commit. npm then writes the exact pin. CI verifies a
changed pin the same way, checks the versioned URL, embedded version and SHA512
integrity, installs it through `npm ci`, and tests the consuming bridge. Never
reference a mutable Git branch or silently select a newer library.

Update the candidate's `CHANGELOG.md` and, for bridge changes, `app/CHANGELOG.md`
sections with the user-visible behavior, upgrade steps, compatibility limits and
rollback instructions. Rollback names the previous stable versions.

Keep these sections short. The `CHANGELOG.md` section becomes the release notes
of every beta and of the stable release, and the app store shows
`app/CHANGELOG.md`:

- Use a flat bullet list without `###` subheadings, one bullet per user-visible
  change. Each bullet starts with the feature or entity name in bold and takes
  at most two sentences, with the issue link, or the PR link when there is no
  issue.
- Leave out root-cause analysis, reporter evidence, diagnostic field lists,
  test-coverage detail and lists of what stays unchanged. They belong in the
  issue, the PR or the documentation, which the bullet can link.
- Give the hardware status in a short phrase, such as "confirmed on hardware",
  "reported, not reproduced" or "experimental, not yet confirmed on hardware".
  A known problem or missing support gets its own bullet. This keeps the
  statuses separate, as the
  [hardware coverage rules](#hardware-coverage-and-release-scope) require.
- Combine dependency and other maintenance updates into one bullet.
- A later PR in the same batch edits the existing bullet. It adds no correction
  or reference to another entry.
- The Upgrade and Rollback paragraph takes at most three sentences. It names a
  compatibility limit only when a supported combination breaks or loses a
  feature.
- A stable batch stays under about 300 words per section.

All Validate checks must pass on the current PR commit. The final **ci** check
fails if any prerequisite failed, timed out, was cancelled or skipped. Protect
`main` by requiring a pull request, up-to-date branches, resolved conversations
and the GitHub Actions `ci` check; disallow force pushes and branch deletion.
No second maintainer approval is required for this single-maintainer project.

After merge, check `ci` on the resulting `main` commit. Branch CI alone is not
release evidence. Each Release run calls the same complete Validate workflow
from its own commit, so the release cannot use an older green run.

On a push to main, Validate also fails when `v<version>` is tagged at an earlier
commit and runtime changed since that tag. This catches a PR that passed while
its version was unpublished and merged after the publication. Open a PR that
raises the version. A tag at the pushed commit passes, so reruns of a published
commit stay green.

## Batch release run

Stable releases happen on request, in one run together with eufy-mega-client.
Issue runs end with a candidate or a beta, not with a stable release. One
approval covers the whole run: the client stable release, the camera release PR
whose merge updates the stable app, and both GitHub releases.

1. Start the merge freeze in both repositories, at the run approval. A hotfix
   has already started it.
2. When the client has an unreleased candidate, release it first with its
   [release guide](https://github.com/keesmod/eufy-mega-client/blob/main/docs/RELEASING.md):
   release PR, rehearsal and publication.
3. Open one camera release PR with these changes:
   - Pin the stable client with `python3 scripts/bump_client.py X.Y.Z` when the
     pin changes. A stable camera release needs a stable client pin.
   - Set the plain integration and bridge versions, the stable parts of the
     candidates, with the recipe above.
   - When the release PR itself changes the bridge runtime, with a new client
     pin or a lock advisory fix, and main has no bridge candidate, set the
     bridge to the next plain patch above the `ha_app` version. Add a dated
     `## X.Y.Z - YYYY-MM-DD` section to `app/CHANGELOG.md` and run
     `python3 scripts/prepare_ha_app.py --release`.
   - When main has no integration candidate, for example in a hotfix right after
     a stable release, set the integration to the next plain patch with the
     recipe above, including `uv lock` and `npm run build` for the card bundle.
     Add a dated `## X.Y.Z - YYYY-MM-DD` section to `CHANGELOG.md` and set the
     README card resource to `?v=X.Y.Z`.
   - Date the heading in `CHANGELOG.md` and, for a new bridge, in
     `app/CHANGELOG.md`. Each section ends with one Upgrade and Rollback
     paragraph that names the previous stable versions. Condense the sections
     this release dates to the changelog rules above before you run
     `prepare_ha_app.py --release`, which copies `app/CHANGELOG.md` into the
     store folders.
   - Run `python3 scripts/prepare_ha_app.py --release` when the bridge version
     changed. It writes `ha_app/` and an existing `ha_app_beta/` at the stable
     bridge. An integration-only release keeps both folders.
   - To bring a development-only lock fix, such as a store-folder advisory, into
     the store folders when main has no bridge candidate, raise the bridge to
     the next plain patch above the `ha_app` version, add a dated
     `## X.Y.Z - YYYY-MM-DD` section to `app/CHANGELOG.md` and run
     `prepare_ha_app.py --release`.
   - Set the README card resource to `?v=X.Y.Z` and replace the current-release
     summary in the README Upgrading section. History lives in `CHANGELOG.md`
     and the release notes.

   It normally changes nothing else. CI runs the release checks on it.
4. Collect the acceptance evidence before the merge, for example from testers of
   the beta app. The merge itself is the stable app update.
5. Merge and wait for `ci` on main. Rehearse and publish that commit right away,
   as described below. Until then, the stable app runs the new bridge while HACS
   still offers the previous integration.
6. Update the maintainer bench and check the result. See
   [development](DEVELOPMENT.md#maintainer-bench).
7. Follow up with the reporters of every issue referenced since the previous
   stable tag. Collect them from `git log --format=%B vPREVIOUS..HEAD`, with
   `refs #N` and `refs <repo>#N`, and from the `keesmod` issue links in the
   released `CHANGELOG.md` and `app/CHANGELOG.md` sections as they stood before
   the release PR condensed them, in `git show <release PR commit>^:<file>`. A
   section that the release PR adds itself is read from the release PR. When
   the run released the client, do the same in eufy-mega-client for its range.
8. Lift the freeze. The run is complete.

## Betas

A beta lets willing testers install a candidate before its stable release. Betas
fall under the standing approval and need no batch run.

1. When the bridge needs unreleased client changes, publish a client beta from
   client main and pin it with `python3 scripts/bump_client.py X.Y.Z-beta.N` in
   a candidate PR.
2. When the bridge candidate is newer than the stable app, open a beta-cut PR
   with `python3 scripts/prepare_ha_app.py --beta`. It writes `ha_app_beta/` at
   the bridge version. Its merge updates the beta app, and the first cut adds
   the beta app to the store. The cut needs an unpublished integration version,
   so open it before the prerelease run. An integration-only beta needs no cut.
3. Run **Release** with the beta version. A beta may be published on its first
   run, with **publish** ticked, without a separate rehearsal. That run still
   validates, builds and verifies the package before it creates the tag. An
   acceptance text without hardware results is enough, for example
   `CI only, no hardware result yet for #149.`

The notes open with a sentence that this is a prerelease of `X.Y.Z` for opt-in
testing, followed by the current `X.Y.Z` section. A beta must be newer than every
public release, stable or beta. After its publication, the next runtime PR raises
`N`, and the next bridge change raises the bridge above the beta folder. HACS
users see a beta only when they select its tag or turn on the Pre-release switch.
See [beta testing](INSTALLATION.md#beta-testing).

## Hotfix lane

A hotfix is a stable release of current main between batch runs, with its own
run approval. There are no release branches. The freeze starts at the hotfix
approval. Revert work that must not ship first, in an ordinary PR under the
candidate rules, and land the fix as a candidate or directly in the release PR.
Then continue with the batch release run from step 3. Release the client first
only in the two cases below, with the client's
[hotfix lane](https://github.com/keesmod/eufy-mega-client/blob/main/docs/RELEASING.md#hotfix-lane),
so that unrelated client candidate work stays unpublished. `--release` also
resets an existing `ha_app_beta/` to the stable bridge, so beta testers run the
hotfix until the next beta cut.

When the fix is in the client, release the client first and pin that version in
the camera release PR. An advisory in a transitive dependency of the bridge can
be fixed in `bridge/package-lock.json` without a client release. That is a
production lock change, so it needs bridge and integration candidates.

When main pins a client beta, the pin cannot be reverted, because the client pin
never decreases. Release a client stable at or above that beta from client main,
with unwanted client work reverted there first, and pin it in the camera release
PR. This also applies when the fix is only in the camera.

## Merge freeze and recovery

From the approval of a batch or hotfix run until the run is complete, only the
PRs of that run merge to main: its release PRs and, in a hotfix, its revert and
fix candidate PRs. Publication uses only the commit that was rehearsed. When a
run stops with `main advanced`, compare the rehearsed commit with current main
and check whether the tag `v<version>` exists. If only documentation changed and
the tag does not exist yet, rehearse and publish current main. A stop just
before the draft becomes public comes after the tag was created, so that version
is used up. A runtime change after the approval, other than the run's own revert
and fix PRs, needs a new approval. Before the release PR merges, such a change
joins the same `X.Y.Z` batch under the candidate rules. It keeps the version
while that beta is unpublished, raises `N` after a published beta, or goes
directly into the release PR.

A tag created at a superseded commit uses up its version, because tags never
move. A runtime PR merged after a release PR has to raise the version, so the
dated version can no longer be published from main. Versions never decrease.
Release the newer version instead and keep the unpublished section as history.
The release notes contain only the new version's `CHANGELOG.md` section, so that
section carries the user-visible changes and upgrade steps of the unpublished
section, including its bridge app update. Its rollback names the last published
stable integration and the bridge that the stable app already runs. The merged
camera release PR has already updated the stable app, so open the next release
PR without delay.

## Dependabot

- Development-only updates, such as bridge `devDependencies` and the frontend
  test tooling, merge as they are once `ci` passes. The bridge ZIP may then
  carry newer development dependencies than the store folder with the same
  bridge version.
- TypeScript in `frontend/` compiles the shipped card. When an update changes
  the rebuilt bundle, the card job fails. That is an integration runtime change,
  so an agent PR supersedes it with the rebuilt bundle, an integration candidate
  and a changelog line, as for a production update.
- A production update changes the bridge runtime and cannot pass the candidate
  rules on its own. An agent PR supersedes it with the same update, candidate
  versions and changelog lines. Then close the Dependabot PR.
- Close security PRs against `ha_app/` or `ha_app_beta/`. Fix the advisory in
  `bridge/`. The store folders follow at the next release or beta cut that
  changes the bridge version. A development-only fix does not raise the bridge
  on its own, so use the release PR step for that case.

## Rehearse and publish

1. Merge the release PR, or the beta candidate and its cut, and wait for `main`
   CI.
2. Open **Actions → Release → Run workflow**, select `main`, enter the version
   without `v`, and leave **publish** unchecked.
3. Inspect the successful run and download its `release-package` artifact. It
   contains integration, bridge and source ZIPs, `SHA256SUMS` and
   `release-manifest.json` with source commit, component versions and file hashes.
4. Name the changed features and affected transport paths. Protocol, device
   commands and media changes need bounded tests on representative affected
   hardware and HA routes, with one controlling bridge, preserved private state
   and verified cleanup. Reviewed community results can supply this evidence.
   Record the exact versions, observation duration, method and anything unproven.
   CI cannot prove physical sound, battery life or a live migration. Changes that
   do not affect hardware need no new physical tests. Record that rationale.
5. Run **Release** again on the same `main` commit and version, tick **publish**,
   and supply a sanitized acceptance summary of one sentence or an evidence link.
   The summary is included in the public release notes. Never include
   credentials, serials, recognized names, private footage or raw diagnostic
   logs.
6. The pipeline repeats validation, checks the requested version and current
   `main`, creates the exact tag and a draft, uploads the tested files, downloads
   and verifies them, then publishes. It downloads and verifies the public assets
   once more. Only the publish job has repository write access.

The main branch must still point at the candidate when publication begins and
immediately before the draft becomes public. If it advanced and the tag does not
exist yet, rerun from current main. An existing tag uses up its version, as
described under the merge freeze. A new version must be newer than every public
release, betas included. Reusing an existing tag at another commit is rejected.
A merge or a pushed tag alone does not publish a release.

## Hardware coverage and release scope

Follow the [community evidence policy](https://github.com/keesmod/eufy-mega-client/blob/main/docs/COMMUNITY_VALIDATION.md).
A missing test for an otherwise implemented model is not a release or upgrade
veto. Keep previously tested combinations with their original versions and dates.
Do not demand every camera model or a fixed number of installations for each
release. Maintainer ownership of the hardware is not required.

State confirmed behavior, reported results, unconfirmed implementation, known
problems and missing support separately. Required software/security checks and
actual protocol, migration and safety gates remain. For a new protocol path or
major migration, arrange voluntary testing of a recoverable candidate before a
stable claim. Publish such a candidate as a beta.

Dependencies must match the release slice. Unchanged mower-map work cannot block
a camera-focused library or camera release. Changed shared behavior still needs
appropriate checks for affected consumers, and map or mower migrations retain
their actual acceptance requirements. Missing expected devices remain a migration
failure. A qualified release does not wait for completion of the whole programme.

For a known regression, identify affected versions, feature, model/topology and
recovery advice. Verify the fix on the affected path before claiming it resolved.
Keep unresolved validation in its existing issue without silently widening a
support claim. Documentation and report-form changes take effect on GitHub after
merge and do not need a product version bump, HA deployment or live-device test.

## Diagnostic release checks

When a release changes diagnostic behavior, include these checks in its existing
validation. The [collection guide](DISCOVERY_DIAGNOSTICS.md) owns user steps and
the [report contract](DEVELOPMENT.md#diagnostic-report-contract) owns field meaning,
privacy bounds and schema compatibility.

- Verify the exact published library URL/integrity and actual installed library
  version, then test the consuming bridge and HA filter with the same report.
  Check supported schema versions and the older-integration fallback explicitly.
- Verify the complete download and normal startup logs with debug disabled,
  including failed setup and rejected devices. Confirm bounded retention, private
  value exclusion and authenticated access. Exercise failure paths synthetically
  without forcing production outages or waking cameras for log collection.
- State separately which bridge, library and integration versions each collection
  method needs. Confirm that the bridge update is available through its documented
  channel and the integration version is publicly released before telling HACS
  users to install it. Until then, document the available bridge-log alternative.
- Update collection instructions, support links and issue-form wording together
  when the process changes. Users should be asked for one complete bounded
  discovery report for missing devices, including accepted rows and context.
- For an authorized deployment, retain backups and verify installed versions and
  the actual log/download route. Record what was observed and what remains
  synthetic or untested. Diagnostics success is not proof of camera hardware or
  media support. Documentation-only changes need no deployment or live check.

## Failure and recovery

The publisher retains the release ID returned when GitHub creates the draft.
Subsequent reads, uploads and publication use that ID. Downloads use asset IDs,
so delayed tag/list indexing cannot hide a draft created by the same run. An ID
read that returns 404 is retried up to four attempts, with 1, 2 and 4 seconds
between attempts and a 10-second timeout per request. Other errors stop the run.
Writes are never retried automatically. If creation has an uncertain outcome or
ID reads remain unavailable, inspect the exact draft and rerun only the failed
job after confirming its tag, commit, notes and assets.

A failed or cancelled build cannot publish. A download, checksum or package
mismatch leaves the candidate as a draft. Rerunning the same commit can resume
missing uploads; reuse the original acceptance summary. Draft notes must match
the candidate before publication. Existing assets are verified and never overwritten. A mismatched
existing asset or an unrelated manual draft requires inspection, not automatic
deletion. Preserve valid published releases and tags.

If a failure occurs after the release became public, inspect the published
assets and run the verification again. The pipeline reports failure; it does not
silently remove a version users may already have installed. An identical already
published candidate is only verified, without uploading or publishing it again.

For a faulty product release, publish a corrected newer version and document
rollback. Do not move its old tag or replace a released file. The consuming
bridge's lockfile must continue to identify the exact library bytes it tested.

## Local checks

Use Python 3.11+ and Node.js 24. GitHub uses bounded Ubuntu jobs.

```sh
python3 scripts/check_workflows.py
python3 -m unittest discover -s scripts/tests -v
python3 scripts/release.py check
python3 scripts/release.py check --base "$(git merge-base origin/main HEAD)"
```

With `--base`, the pull request rules run against that commit. This
approximates CI, which checks the pull request's merge commit against main.
Rebase onto `origin/main` first for an exact result. The published lookup and
the client pin verification need an authenticated `gh` session.

From a clean committed checkout, build the complete local bundle into a new
empty directory, then verify it:

```sh
python3 scripts/release.py build --directory /tmp/eufy-release-candidate
python3 scripts/release.py verify --directory /tmp/eufy-release-candidate
```

Packaging selects tracked files from explicit source directories. Untracked
credentials, caches and local scratch files are excluded. ZIP members and bytes
are checked against the source checkout. Releases keep integration and bridge
versions distinct when only the integration changed.

Actionlint and GitHub Actions are pinned to verified versions/checksums. Update
the pins deliberately and run the workflow validator. `scripts/release.py`,
`scripts/check_workflows.py`, `scripts/tests/test_release.py` and
`.github/workflows/release.yml` are byte-identical in both repositories. Apply
common fixes to both. Project-specific metadata, version rules, store folder and
package checks live in `release_project.py` and are tested in
`scripts/tests/test_project.py`.
